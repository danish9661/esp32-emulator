about the emulator

A whole ESP32, simulated honestly.

esp32emu boots the real ESP32 boot ROM and runs real compiled Arduino / ESP-IDF firmware on a cycle-counted dual-core Xtensa LX6 model. There is no instruction-set paraphrase and no UART spoofing: every byte on the demo terminal was transmitted by emulated silicon.

How it works

Four layers, each doing the job it is best at.

1 · Core engine (Rust to WASM)

Both LX6 cores execute inside a single WebAssembly module compiled from Rust. A batched core_run export advances up to 512 interleaved iterations per host call, with CCOUNT sync per instruction. The core is self-timed: it tracks its own cycle count and fast-forwards idle stretches straight to the next timer alarm.

2 · Native peripherals (same module)

UART, GPIO, SPI, I2C, timers, RMT, TWAI, ADC, touch, SDMMC, EMAC, WiFi MAC and more live in Rust behind a page-table dispatch. A full firmware run issues zero fallback calls into JavaScript for peripheral traffic.

3 · Host bridges (JavaScript)

What cannot live in WASM stays out: the worker-thread host, the SharedArrayBuffer UART ring, the simulation clock source, the WiFi gateway socket, and the compile service that turns Arduino sketches into flash images.

4 · This page

The demo tab spawns the same worker the Node test-suite uses, feeds it a prebuilt 4 MB flash image, and renders UART0 into the terminal. The ESP32-CAM toggle applies the real module preset: 4 MB PSRAM and the AI-Thinker pinout.

Speed, measured not marketed

Throughput is reported in MIPS: millions of simulated instructions retired per wall-clock second. Two numbers matter.

709 MIPS
steady-state, GPIO firmware, run/stop hot loop
~58
M instr/sec, batched core_run path (lab bench)
live
every demo run prints its own MIPS line
0
JS fallback calls on the peripheral hot path
Why two numbers? The 709 MIPS figure is the whole simulator (both cores, idle fast-forward, host loop) on the demo firmware. The ~58 M instr/sec figure is the core engine alone on a CPU-bound loop. Idle or delay-heavy firmware is dominated by fast-forward, not instruction throughput — which is exactly what real silicon does too.
